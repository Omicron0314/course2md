# 设置区域独立交叉审查 · v2

日期：2026-09-09。审查者：fresh_flow_audit，未实现设置页面。本次证据为同目录的 `v3-settings-generation-top.jpg`、`v3-settings-generation-ai.jpg`、`v3-settings-ai-service-unit.jpg`、`v3-settings-application.jpg`、`v3-settings-model-resources.jpg`、`v3-settings-resources-about.jpg` 与 `v3-07-settings-during-source.jpg` 七张原生原图及配套 `.ax.txt`。全部是约 1068×768 的普通窗口、100% 字号。本次未操作 GUI、未修改设置源码、未运行 cargo。

生成页现在按字幕、语音识别、AI 处理、额外文件排列；应用页先给运行检查及默认模型，再给引导和关于。二者比 v1 更符合用户来此修改默认值或解决准备问题的用途。但这组原图还不足以作验收结论：长服务仍在原图中溢出，此外应用页对健康模型的动作强调和“当前”的范围仍有实质歧义，自动导出也缺少清楚的保存与取用说明。

## 仍需处理的判断

### 1. 已就绪的模型仍被呈现为需要继续准备（P2）

`v3-settings-application.jpg` 同时显示“已验证可加载”“验证后模型文件未改变”，却继续给出常驻的“准备时可能下载模型，课程内容不会上传”，并将“重新验证加载”绘为这一屏唯一蓝色主按钮。旁边还有“重新检查模型”，上方另有“重新检查环境”。当前健康状态并不缺下一步，页面却仍将重复维护检查作为最强动作。

这不是对准确性的泛泛怀疑。源码中“重新检查模型”调用本地状态检查；“重新验证加载”进入真实的模型准备流程。二者成本与用途不同，但在这一健康视图中仅靠“检查”和“验证”两个近义词区分。用户可能为了放心开始转换，反复执行已经完成的准备。

建议保留两个维护能力，但让状态决定主次：缺失、部分下载时突出“下载并准备／继续准备”；已缓存但未验证时突出加载验证；已验证且文件未改变时明确已准备好，将刷新文件状态和再次测试加载降为次级动作。下载范围说明应邻接确有下载可能的准备状态；无需在成功状态继续铺陈为下一步要求。不要通过再加一个总状态卡解决动作语义。

### 2. “当前模型”没有说明它检查的是生成默认值（P2）

应用页的标题是“当前模型”，但 `model_diagnostics_panel` 通过 `default_model_request` 读取 `preferences.generation().options`，并不读取当前草稿的单次调整或正在处理任务的冻结计划。应用也允许用户处理一个任务时进入设置。因此“当前”容易被读成正在运行的模型，在排查某一任务为何用 CPU、为何访问服务时尤其误导。

应直接叫“默认识别模型”，或用同样清楚的短句限定为“后续转换的默认模型”。不要为了让这个检查追随任务而改写冻结计划。当前源码已经将另一个活动下载单列为“正在准备的模型”，这项区分应保留。

### 3. “同时导出”说明了格式，却没有说明这些文件去哪里（P2，闭环仍需动态复核）

`v3-settings-generation-ai.jpg` 的“同时导出”下面只有“笔记会自动保存在应用内；按需同时保存以下文件”，旁边是 Markdown 包、网页文件、JSON 数据。用户能理解这三项可选，也不会把它们当作内部阅读的前置条件；但无法判断勾选后会出现保存对话框、写入默认导出目录，还是跟随笔记存放。

源码核对表明，转换时这些文件写入已发布笔记版本内的 `exports` 目录；阅读器的手动导出则是另一条选择目标位置的流程。现有“打开／显示笔记保存位置”可以到达相关目录，但这张设置图没有建立两者关系。此处不是已确认的文件丢失，而是设置承诺和取用位置的信息缺口。

建议就近说明“生成结束时与笔记一起保存，可从笔记的保存位置取用；也可在阅读时另存”，措辞按最终实际入口压短。必须实际勾选至少一种格式完成一次生成，确认结束后有可理解的取用入口，并核对自动导出与阅读器另存行为不会互相覆盖。仅证明磁盘上有文件不能关闭这一项。

### 4. 已知布局失败仍是这组原图的有效事实（待 v4 复拍）

`v3-settings-ai-service-unit.jpg` 中 AI 服务的多选项横轨越过右边界，当前服务名称与模型被截掉。这里的失败不只是文字不完整：用户无法辨认实际默认绑定与修复时新增版本。当前源码已改为单个当前值下拉加编辑，由设置实现者负责；本审查没有把源码存在当成原生复核通过。

根代理另已修“同时导出”复选框组的首行对齐，以及设置滚动条与右侧状态固定 12px 间距。这两项不用重做已知诊断，但 v4 必须重看整组及弹出菜单。尤其下拉要同时清楚表达当前值、另一个可选服务、同一服务的旧默认配置与新版，而不依赖窗口外的长串后缀。

## 接下来必须实际访问的状态

1. v4 的单值服务下拉：长名称、多个不同模型、同服务旧默认与新版、已停用当前值；打开菜单后可读当前绑定，编辑后返回仍能辨认作用范围。
2. Ready、Cached、Missing、Partial、检查失败的模型页；每一种都要确认一句主结论和适合该状态的主要动作。正在准备另一个模型时，默认模型与活动下载不能混成同一个“当前”。
3. 草稿单独选 CPU 或其他模型后进入应用页；再以冻结任务运行期间打开设置，证明默认模型检查不会被理解为或改变该任务配置。
4. 勾选自动导出后的真实完成与文件取用；导出失败可恢复，正常可读正文不受损，之后手动另存路径独立且结果可找。
5. 外观跟随系统／深色、主题菜单、125／150／200% 字号与窄窗口；同时重看首行对齐、右侧状态和下拉编辑动作关系。当前 100% 原图的空间余量不能代替这些状态。
6. AI 两个主开关关闭、无服务、测试中修改服务字段、401、429／5xx、取消修复、只保存；需确认现有说明与错误动作仍对应当下实际启用的能力和配置。

本次新增核心问题是健康状态仍强推重复准备，以及默认模型被泛称为“当前”。自动导出的位置说明也应补齐并完成真实取用验证。已有修复计划和源代码变化没有被当作设置区验收结论。
