## 为什么上一轮仍比 CLI 复杂

上一轮主要改善了控件与画面，却没有以“拿到第一篇笔记，第二篇少做什么”为首要验收对象。CLI 也有首次配置与失败分支；应比较同一目标下用户必须作出的决定、发出的动作和绕路，不能只比较按钮或命令行数量。

| 根因 | 原来造成的实际负担 | 本轮修正方向 |
| --- | --- | --- |
| 将读取、确认、计划等内部阶段固化为页面步骤 | 正常预检结束仍等用户再发一次生成意图；自动字幕失败也成为手动选路的前提 | 一次生成意图持续到可提交；只有选择不明确、授权变化或可修复障碍才暂停。自动本机路线与固定字幕/服务选择分别处理 |
| 把默认配置、单次覆盖和内部服务版本混在一起 | 初次服务未成为默认，新视频继续沿用上一条的库/临时覆盖，编辑服务还要理解版本 | 配置一次后复用；新输入采用当前默认，已提交任务保持快照；普通界面只在必要时区分当前与更新配置 |
| 把全局导航等同上下文返回，把离开等同取消 | Reader 无法直接回库或从设置回原文；未保存服务输入丢失；完成结果先绕去任务 | 当前导航可再次激活，设置提供返回笔记，临时离开保留私有编辑，结果动作直达正文 |
| 只为最初入口设计成功路径，缺少修复后的继续 | 保存新服务能继续，选择已有服务、修复存储或恢复默认却停住；手动移动库后无恢复入口 | 成功修复唤醒正确 pending 代次；明确取消和换源使旧意图失效；同库身份匹配后重新定位，不假造新库或迁移备份 |
| 用完整截图与测试数量代替任务验收 | 能确认控件整齐，不能确认重复配置、操作死路、结果归属与数据保留 | 先走首次任务、重复使用和恢复，再审画面；截图、动作、源码、测试和磁盘证据分别注明范围 |

设计依据已查阅 Apple 当前 [Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding)、[Settings](https://developer.apple.com/design/human-interface-guidelines/settings)、[Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) 与 [Offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help)：引导可跳过、非必要配置延后、软件检测可知事实、反馈贴近当前任务。项目据此保持的边界是：用户决定内容、必要选择与实际后果；软件复用默认并推进准备。固定选择、文件替换及结果不确定的外部重发不能以“自动”为名越过。
