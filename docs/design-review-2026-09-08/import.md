## 实现分工与必须保留的行为

- 本审查代理后续仅修改 `import_ui.rs`；全局标题栏、主题 token、共享 `badge`、Material 资源由主代理负责，最近笔记与任务状态由相应页面代理负责。
- 现有草稿身份、异步结果代次校验、明确字幕意图、旧字幕保留、服务版本、去重及生成参数快照已有真实验证，不得为了简化界面改变它们。
- 动效应绑定具体事件：忙碌指示持续期间、来源确认、错误进入、从属选项展开/收起。禁止每次重绘重新播放整个表单；禁止虚构百分比、等待时间或成功动画。
- 所有新按钮图标采用统一 Material 家族；YouTube/Bilibili 使用品牌资源。共享 helper 应统一图标与文字间距，不能靠各页临时补空格。

## 第五轮：窗口失去下一帧请求的原生回归

I30 / P1：design05 在 860×620 窗口启动后停留在“正在读取笔记”；快捷键可触发一次更新，但随后导航选中态停在动画起点，读取仍不完成。主代理记录了交互现象，本代理独立审查 `design05-sample.txt` 与固定上游源码：采样的主线程在正常 AppKit / CFRunLoop 等待，没有阻塞锁或持续同步绘制栈。采样支持“没有后续工作被唤醒”，本身不能单独定位根因。

确定的丢失路径在原 `zed-macos-window.patch`：`display_layer` 和显示刷新回调先 `take()` 帧回调，再调用 GPUI；GPUI 在绘制后若仍有 dirty 或下一帧动画，会调用 frame waker。原补丁因 callback 此时为 `None` 直接返回，丢弃了该请求；帧回调随后确实会还原，但 `start_display_link` 遇到 occluded 或暂时没有屏幕时直接返回。GPUI 的 dirty 已置位，后来的普通通知不会再次从 clean 转为 dirty，因此窗口可以一直停在旧画面。这是请求丢失，不是帧回调丢失，也不是笔记读取业务死锁。

修复仍放在受版本管理的 `desktop/patches/zed-macos-window.patch`：每窗口将需求合并到 16ms 后的主线程任务，届时调用 AppKit `setNeedsDisplay`；即使需求来自正在绘制的帧也保留。定时器运行时若回调暂不可用，继续延迟重试；唤醒前清除合并标记，确保唤醒期间产生的新需求可以再排队。闭包只持有窗口弱引用并检查关闭标志。没有同步调用 draw，也没有在当前 CA 绘制事务中反复失效窗口。
